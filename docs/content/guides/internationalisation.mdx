# Internationalisation

Le template sert **plusieurs langues simultanément**. L'application de démonstration vit
sous `/demo/<langue>` — `/demo/fr/…`, `/demo/en/…` —, la langue d'un nouveau visiteur est
déduite de son navigateur, et un sélecteur dans le header lui permet d'en changer sans
quitter la page qu'il lit.

Cette page décrit d'abord **le mécanisme**, puis les **trois gestes de maintenance** :
ajouter une chaîne, ajouter une langue, traduire du contenu. Si vous ne lisez qu'une
section, lisez celle-là.

## Deux couches, et pourquoi elles sont séparées

Le point de départ est une contrainte du mode de distribution. Un composant de ce dépôt
peut arriver chez vous de deux façons : avec tout le projet (*Use this template*), ou
**seul**, par `npx shadcn add`. Dans le second cas il n'y a ni manifeste, ni provider, ni
dictionnaire — et il doit fonctionner quand même.

D'où deux couches, dont une seule dépend de l'autre.

### Couche 1 — chaque composant porte ses libellés

Un composant traduisible déclare une constante de module avec des défauts français, et
accepte une prop `labels` fusionnée par-dessus :

```jsx
const DEFAULT_LABELS = {
  clear: 'Effacer la recherche',
  suggestions: 'Suggestions de recherche',
};

const SearchBar = ({ labels: labelOverrides }) => {
  const labels = mergeLabels(DEFAULT_LABELS, labelOverrides);
  // …
};
```

Trois règles font tout le motif :

1. **Un objet unique**, `labels`, et non une prop par chaîne. Sinon un composant qui
   affiche six textes prend six props.
2. **Les défauts dans une constante de MODULE**, pas dans la valeur par défaut de la
   prop. C'est ce qui rend la fusion *partielle* possible : un appelant qui ne traduit que
   deux libellés sur six garde les quatre autres.
3. **Aucune clé sans usage.** Le dictionnaire décrit ce que le composant affiche.

`mergeLabels` n'est pas un simple `{ ...defaults, ...overrides }`. Il **refuse** les
surcharges `null`, `undefined`, vides ou blanches, et les clés inconnues du composant.
C'est la garantie d'accessibilité du template : **une traduction incomplète ne peut pas
produire un `aria-label` vide**. Elle produit du français.

### Couche 2 — l'application remplit ces props

Le dictionnaire de `src/i18n/dictionaries/` n'est rien d'autre que l'union des formes
`DEFAULT_LABELS`, rangées par espace de noms :

```js
// src/i18n/dictionaries/fr.js
const fr = {
  header:  { skipToContent: 'Passer la navigation', /* … */ },
  table:   { reset: 'Réinitialiser', /* … */ },
  filter:  { addCriterion: 'Ajouter un critère', /* … */ },
};
```

Le layout de langue le charge une fois et le distribue :

```jsx
// src/app/(site)/demo/[locale]/layout.jsx
const dictionary = await getDictionary(locale);

<Header labels={dictionary} locale={locale} />
```

La couche 2 remplit les props de la couche 1, **jamais l'inverse** : aucun composant ne
lit le dictionnaire, aucun n'importe `src/i18n/`.

> **Pourquoi pas `next-intl` ou `react-i18next` ?** Parce qu'ils imposeraient un provider
> et un runtime à **tout** consommateur du registry — y compris à celui qui installe un
> seul bouton — et leur format de messages à celui qui a déjà sa propre chaîne i18n. Pour
> 190 libellés, le coût n'est pas justifié. Rien ne vous empêche d'en brancher une :
> remplissez la prop `labels` depuis votre librairie, les composants ne verront pas la
> différence.

## Les trois gestes de maintenance

### 1. Ajouter une chaîne à un composant

Trois éditions, dans cet ordre :

```jsx
// 1. la clé et son défaut français, dans le composant
const DEFAULT_LABELS = {
  clear: 'Effacer la recherche',
  export: 'Exporter la sélection',   // ← nouvelle clé
};
```

```js
// 2. la même clé dans src/i18n/dictionaries/fr.js, sous le bon espace de noms
searchBar: {
  clear: 'Effacer la recherche',
  export: 'Exporter la sélection',
},
```

```bash
# 3. le script vous dit ce qu'il reste à faire
npm run check:i18n
#   en.js → searchBar.export : clé manquante
```

Vous n'avez rien à mémoriser : **`check:i18n` est la liste des choses à faire**. Il est
dans la chaîne `verify` et dans la CI avec `--strict`, donc un oubli ne peut pas être
fusionné.

### 2. Ajouter une langue

Cinq lignes, aucune dans un composant :

```jsonc
// config/site.config.json — l'ordre compte (voir plus bas)
"locales": ["fr", "en", "es"],
"defaultLocale": "fr"
```

```js
// src/i18n/getDictionary.js — l'import doit rester LITTÉRAL
case 'es': {
  const { default: es } = await import('./dictionaries/es');
  return deepMerge(fr, es);
}
```

```js
// src/i18n/formats.js — les conventions, qui ne sont pas des traductions
es: {
  intlLocale: 'es-ES', currency: 'EUR', percentSuffix: ' %',
  dateMask: 'DD/MM/AAAA', dateOrder: 'DMY', firstDayOfWeek: 1,
  d3Locale: 'es-ES', siPrefixBillion: 'G',
},
```

Plus le fichier `src/i18n/dictionaries/es.js` (copiez `fr.js` et traduisez), et les deux
lignes d'import de locale d3 dans `src/i18n/d3Locale.js`.

**Rien d'autre.** Les routes, l'index de recherche et la suite Playwright se déduisent :
`generateStaticParams` fait le produit cartésien des langues et des pages, et
`e2e/helpers/routes.ts` fait le même. Ajouter une langue double la couverture du test de
fumée sans qu'une ligne de test ne bouge.

Tant que `es.js` est incomplet, les clés manquantes s'affichent **en français** — le site
reste utilisable pendant la traduction.

### 3. Traduire du contenu

Le contenu n'est pas dans les dictionnaires : il est dans `config/`. Tout champ de texte y
accepte **deux formes** :

```jsonc
{
  "path": "/pib",
  "name": "PIB",                                  // identique partout
  "description": { "fr": "Produit intérieur…", "en": "Gross domestic…" }
}
```

La forme chaîne n'est pas une tolérance héritée : c'est la forme **juste** pour un sigle,
un symbole (`=`, `≥`) ou un nom propre. L'imposer sous forme d'objet à trois clés
identiques serait du bruit, et inviterait à traduire ce qui ne doit pas l'être.

Trois fichiers sont concernés — `config/site.config.json` (titre, description, arbre de
navigation), `config/content/home.json` (page d'accueil) et
`config/filter/operations.json` (libellés d'opérateurs).

Ce qui ne se traduit **jamais** : les `path` d'URL, les `value` d'opérateurs et de
connecteurs (ce sont des identifiants sérialisés dans le filtre), les chemins d'images.

```bash
npm run validate:config   # la langue par défaut est-elle présente partout ?
npm run check:i18n        # une langue déclarée est-elle oubliée quelque part ?
```

## Ce que la traduction ne couvre pas : les formats

`1 234,5` contre `1,234.5`, `31/12/2026` contre `12/31/2026`, la semaine qui commence
lundi ou dimanche, l'espace avant le signe pourcent. Ce ne sont pas des libellés : ils
vivent dans `src/i18n/formats.js` et pilotent `Intl` **comme** d3.

C'est le point qui mérite le plus d'attention si vous reprenez ce code, parce que le dépôt
s'y est déjà trompé : `d3-format` et `d3-time-format` ont leur **propre** notion de locale,
indépendante d'`Intl`, et leur défaut est `en-US`. Avant que ce mécanisme n'existe, les
axes des graphiques affichaient `1,234.5` et des mois `Jan`/`Feb` à côté d'un tableau
formaté `1 234,5` — sur le même écran.

La règle qui l'empêche de revenir : **aucun `import { format } from 'd3-format'` dans le
dépôt**. On passe par `d3LocaleFor(locale)`, qui renvoie des formateurs liés à une langue
sans toucher à l'état global de d3 — indispensable au build, où les pages françaises et
anglaises sont rendues dans le même processus Node.

## Le routage

```
/                       site de documentation (celui que vous lisez) — monolingue
/demo                   porte d'entrée : négocie la langue et redirige
/demo/fr/…              application, en français
/demo/en/…              la même, en anglais
```

La langue est un **segment d'URL**, donc une dimension de build : chaque paire
(langue, page) est un fichier écrit par `generateStaticParams`. Ce n'est pas un détail
d'implémentation — c'est ce qui rend chaque page partageable, indexable, et servie
directement dans la bonne langue sans clignotement.

Le `localStorage` et le cookie ne mémorisent qu'une **préférence**, consultée uniquement
par `/demo` pour choisir où envoyer un visiteur qui n'a pas précisé de langue. Ils ne
décident jamais de ce qui est rendu.

### La négociation, et pourquoi elle est côté client

Le déploiement de référence est un **export statique** (GitHub Pages). Next refuse un
`middleware.ts` sous `output: 'export'` : il n'y a ni serveur pour lire `Accept-Language`,
ni redirection 30x. `/demo` est donc une page réelle qui choisit dans le navigateur :

1. un choix explicite mémorisé (`localStorage`), qui prime — quelqu'un dont le navigateur
   est en anglais mais qui a choisi le français veut le français ;
2. `navigator.languages`, les préférences du système ;
3. `site.defaultLocale`.

L'ordre de `site.locales` compte à l'étape 2 : un navigateur qui demande `pt` sans région,
face à `["pt-BR", "pt-PT"]`, obtient la **première** variante déclarée.

Un `<noscript>` liste les langues en clair : sans lui, l'application serait inatteignable
sans JavaScript.

### Si vous déployez sur un serveur

`examples/middleware.ts` fait la même négociation avec une vraie redirection 307. Il est
livré **hors** de la racine du projet à dessein : à la racine, Next ferait échouer
`npm run build:docs`.

```bash
cp examples/middleware.ts ./middleware.ts
```

Il appelle **la même** fonction `negotiateLocale` que le repli client : les deux chemins
ne peuvent pas diverger.

## Deux pièges à connaître

### Les libellés dynamiques sont des gabarits, pas des fonctions

```js
sortBy: 'Trier par {column}',                    // ✅
sortBy: (column) => `Trier par ${column}`,       // ❌
```

Le dictionnaire est chargé par un Server Component puis passé en prop à des composants
clients. **Une fonction ne traverse pas cette frontière** — React lève « Functions cannot
be passed directly to Client Components ». D'où `interpolate(labels.sortBy, { column })`.

Les trous sont **nommés** et non positionnels parce que l'ordre des mots n'est pas
universel : c'est précisément ce qu'une concaténation en JSX empêche de traduire.

Quand le trou porte du balisage — un `<code>`, un lien — utilisez `interpolateNodes`, qui
substitue des éléments React au lieu de texte. La phrase reste entière dans le
dictionnaire, donc réordonnable.

### Les pluriels passent par `Intl.PluralRules`

```js
rowCount: { one: '{count} ligne', other: '{count} lignes' },
```

Le motif `n > 1 ? 's' : ''` qui traînait dans le dépôt est faux deux fois : l'anglais met
zéro au pluriel (`0 rows`), et `1,5 ligne` est un singulier en français. `pluralize` lit
les règles de la langue au lieu de coller un « s ».

## Ce qui reste monolingue, et pourquoi

**Ce site de documentation.** Il documente le template ; il n'est pas un livrable de votre
projet, et vous le supprimerez sans doute. Le traduire aurait doublé un corpus de 29 pages
sans rien apprendre à personne.

Conséquence visible dans le code : `<html lang>` est écrit par le layout racine, qui est
au-dessus du segment `[locale]` et ne peut donc pas le lire. Trois mécanismes se
complètent pour que la langue soit malgré tout juste : le layout de langue pose `lang` sur
sa propre racine (WCAG 3.1.2), un script inline corrige `<html lang>` avant le premier
paint, et `LocaleProvider` le maintient lors des navigations clientes.

**Si vous supprimez la documentation, ce détour disparaît** : `[locale]` devient votre
premier segment, son layout devient le layout racine, et vous écrivez simplement
`<html lang={locale}>`.

Enfin, `src/features/chart/sources/demoData.js` reste en français : c'est un **jeu de
démonstration**, pas de l'interface. Vous le remplacerez par vos données.

## Exemple complet : passer le template en anglais seul

Vous ne voulez pas de site multilingue, juste un site anglais.

```jsonc
// config/site.config.json
"site": {
  "title": "Macroeconomic Observatory",
  "description": "Macroeconomic series and projections.",
  "locales": ["en"],
  "defaultLocale": "en"
}
```

```bash
npm run validate:config
npm run check:i18n        # signale fr.js présent mais non déclaré — sans gravité
npm run dev
```

Les libellés d'interface viennent désormais de `en.js`, les nombres et les dates des
conventions `en-US`, et l'URL est `/demo/en/…`. Supprimez `fr.js` et sa branche dans
`getDictionary.js` si vous ne comptez jamais y revenir — mais gardez à l'esprit que la
**référence** de `check:i18n` est la langue par défaut : c'est désormais `en.js` qui joue
ce rôle.
