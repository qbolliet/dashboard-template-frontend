# Alimenter la barre de recherche

La barre de recherche du header ne connaît aucune liste de suggestions. Elle consomme
`public/search-index.<langue>.json` — un fichier PAR LANGUE depuis l'ajout de
l'internationalisation —, **dérivé de `config/site.config.json` au build** par
`scripts/build-search-index.js`.

C'est ce qui garantit qu'elle ne peut pas mentir : navigation et recherche sont produites à
partir du même fichier, par les mêmes fonctions — `resolveNavigationTree` puis
`flattenNavigation`, exactement celles qu'utilise la route attrape-tout pour énumérer les
pages. Une page qui existe est indexée ; une page qui disparaît sort de l'index au build
suivant. Il n'y a rien à synchroniser.

## Ce que contient une entrée

```json
{
  "title": "PIB",
  "path": "/demo/fr/comptabilite-nationale/france/pib",
  "type": "indicator",
  "description": "Produit intérieur brut, en volume, base 2020.",
  "keywords": ["GDP", "produit intérieur brut"],
  "breadcrumb": ["Comptabilité Nationale", "France"]
}
```

`title` et `path` viennent du `name` et du chemin **absolu** du nœud — les préfixes de
montage et de langue compris, sans quoi chaque suggestion mènerait à un 404. `description`
vient du nœud et vaut la chaîne vide s'il n'en a pas.

`keywords` porte les synonymes déclarés sur le nœud (voir plus bas). Ils sont **cherchés
mais jamais affichés** : c'est le vocabulaire par lequel on arrive à la page, pas ce qu'on
lit dessus.

`breadcrumb` porte les **libellés** des pages parentes, racine d'abord. C'est la clé de deux
comportements : « pib france » trouve la page alors qu'aucun champ ne contient les deux
mots, et trois pages « PIB » sous trois pays différents s'affichent de façon distinguable —
le fil d'Ariane est rendu en retrait du titre.

La profondeur d'une page n'est pas stockée : elle **est** son nombre d'ancêtres, et le tri
la lit sur `breadcrumb.length`. L'index ne porte rien qui se dérive.

## Comment une requête est appariée

Le moteur tient dans `src/features/header/utils/searchMatch.js`. Trois règles :

1. **Tous les termes doivent être trouvés**, chacun dans le champ qu'il veut. « pib france »
   fonctionne parce que le premier terme est dans le titre et le second dans le fil
   d'Ariane. Un terme introuvable partout disqualifie l'entrée.
2. **Chaque terme est cherché en préfixe de mot**, jamais en sous-chaîne : `conso` trouve
   « Consommation », `sommation` ne la trouve pas. C'est la sémantique d'un champ
   d'autocomplétion — on complète un mot commencé. La contrainte du point 1 assure la
   précision.
3. **Les champs sont pondérés** — titre 10, mots-clés 6, fil d'Ariane 3, description 1 — et
   chaque terme marque le score de son meilleur champ. Deux bonus s'ajoutent : +2 si le mot
   est trouvé entier plutôt qu'entamé, +3 si le champ commence par le terme. Le total classe
   les suggestions ; à égalité, la page la moins profonde passe devant, puis c'est l'ordre
   du manifeste qui départage.

La comparaison ignore la casse et les accents. L'élision et le trait d'union sont traités
par le **découpage** — « l'emploi » donne deux jetons, « Bouches-du-Rhône » en donne trois —
et jamais par une réécriture de la chaîne, qui décalerait le surlignage.

Il n'y a **pas** de tolérance aux fautes de frappe : `pbi` ne trouve pas « PIB ». C'est un
choix, pas un oubli — sur un catalogue de quelques dizaines d'entrées, une distance
d'édition produit plus de faux positifs qu'elle ne rattrape de fautes. Le lieu où l'ajouter,
le jour où le corpus le justifie, est `matchTermInField`.

Deux seuils, déclarés en tête de `SearchBar.jsx` : deux caractères minimum avant d'afficher
quoi que ce soit, dix suggestions au maximum.

## Déclarer des synonymes

`keywords` sur un nœud du manifeste : les termes sous lesquels la page doit être trouvée
sans qu'ils apparaissent à l'écran — sigles, anciennes appellations, vocabulaire d'un autre
métier.

```jsonc
{
  "path": "/comptabilite-nationale",
  "name": { "fr": "Comptabilité Nationale", "en": "National Accounts" },
  "type": "indicator_group",
  // Forme simple : les mêmes termes dans toutes les langues.
  "keywords": ["INSEE", "SEC 2010"]
}
```

```jsonc
{
  "path": "/recettes-publiques",
  "name": { "fr": "Recettes Publiques", "en": "Public Revenue" },
  "type": "indicator",
  // Forme traduite, quand les synonymes diffèrent d'une langue à l'autre.
  "keywords": {
    "fr": ["impôts", "prélèvements obligatoires", "fiscalité"],
    "en": ["taxes", "tax revenue"]
  }
}
```

C'est la même duplicité que `name` et `description` : un tableau nu pour ce qui ne se
traduit pas, une carte de langue sinon. `npm run validate:config` vérifie la forme, et
`npm run check:i18n` signale une langue déclarée mais non couverte.

Sur un catalogue de cette taille, **une liste tenue à la main bat n'importe quelle
extraction automatique de mots-clés** : les titres de page font trois mots, il n'y a rien à
extraire d'un texte qui n'existe pas.

L'index est chargé **au premier focus** du champ, pas au montage du header : la quasi-totalité
des visites ne touchent jamais la recherche, et il serait inutile de payer la requête à
chaque navigation. Un second focus pendant que le premier chargement est en vol réutilise la
même promesse.

## Retirer une page de l'index

`searchable: false` sur un nœud. La page reste visible dans la navigation et reste
navigable — seule son indexation est désactivée. Utile pour les pages techniques ou les
bancs d'essai.

```jsonc
{
  "path": "/diagnostics",
  "name": "Diagnostics",
  "type": "about",
  "searchable": false
}
```

La clé absente vaut `true`. Le défaut est appliqué par les consommateurs
(`node.searchable !== false`), pas injecté par le validateur : les `default` du schéma sont
documentaires, ils s'affichent en infobulle et ne mutent pas vos données.

## Indexer autre chose que des pages

Le manifeste ne décrit que les **pages**. Un catalogue plus fin — les variables d'un
indicateur, les séries, les entités d'un référentiel — se remonte de l'API au build, et
s'ajoute à l'index avec la même forme d'entrée.

Une seule condition, et elle est structurelle : **chaque entité doit pointer vers une page
qui existe.** L'index n'est pas un moteur de recherche, c'est une table de raccourcis vers
des URL — une entrée dont le `path` ne correspond à aucune route mène au 404.

Le point d'extension est signalé en commentaire dans `scripts/build-search-index.js`, juste
avant l'écriture du fichier. Deux remarques avant de l'utiliser :

- **Le snippet du commentaire charge le client API par `import()`.** Cela ne fonctionne pas
  tel quel : les modules de `src/lib/api/` s'importent entre eux sans extension de fichier
  (`from './gql'`), ce que le résolveur ESM natif de Node ne résout pas — l'appel échoue en
  `ERR_MODULE_NOT_FOUND`. Adressez l'endpoint par `fetch`, comme ci-dessous.
- **Prévoyez le cas hors ligne.** Ce script tourne à chaque `npm run dev` et à chaque build.
  S'il lève quand l'API est injoignable, il bloque le développement de toute l'équipe pour
  une raison qui n'a rien à voir avec la recherche. Journalisez et continuez avec les seuls
  nœuds du manifeste.

## Exemple complet

Indexer les champs du catalogue en plus des pages, pour qu'une recherche sur « chômage »
mène à la page qui expose cette variable.

```js
// scripts/build-search-index.js — le fichier existant, complété.
// Seuls les ajouts sont commentés ; le reste est inchangé.

const fs = require('fs');
const path = require('path');
const { pathToFileURL } = require('url');

const PROJECT_ROOT = path.join(__dirname, '..');
const CONFIG_PATH = path.join(PROJECT_ROOT, 'config/site.config.json');
const OUTPUT_DIR = path.join(PROJECT_ROOT, 'public');
const outputName = (locale) => `search-index.${locale}.json`;

const importEsm = (filePath) => import(pathToFileURL(filePath).href);

// ─── AJOUT — interrogation de l'API ──────────────────────────────────────────
// Par fetch et non par import du client : les modules de src/lib/api/ s'importent
// sans extension de fichier, ce que le résolveur ESM de Node ne sait pas suivre.
const ENDPOINT = process.env.NEXT_PUBLIC_API_URL;

const GET_CATALOG_SCHEMA = `
  query GetCatalogSchema {
    getCatalogSchema { name label sqlType isCategorical }
  }
`;

/**
 * Runs a GraphQL document against the configured endpoint.
 *
 * @param {string} document - Query document.
 * @returns {Promise<Object>} The GraphQL `data` object.
 * @throws {Error} On a transport error or any GraphQL error.
 */
async function query(document) {
  const response = await fetch(ENDPOINT, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ query: document }),
  });

  if (!response.ok) throw new Error(`HTTP ${response.status}`);

  const { data, errors } = await response.json();
  if (errors?.length) throw new Error(errors[0].message);

  return data;
}

/**
 * Builds one search entry per catalog field, pointing at the page that exposes it.
 *
 * Failure is NOT fatal: this script runs on every `npm run dev`, and an unreachable
 * API must not block a developer whose work has nothing to do with search. On error,
 * the index falls back to the manifest nodes alone.
 *
 * @param {Array<Object>} pages - The manifest entries already built.
 * @returns {Promise<Array<Object>>} The field entries, empty on failure.
 */
async function buildFieldEntries(pages) {
  if (!ENDPOINT) return [];

  // La page vers laquelle pointer : le premier indicateur de l'index. À remplacer par
  // votre propre correspondance champ -> page si elle est plus fine.
  const target = pages.find((entry) => entry.type === 'indicator');
  if (!target) return [];

  try {
    const { getCatalogSchema } = await query(GET_CATALOG_SCHEMA);

    return getCatalogSchema.map((field) => ({
      title: field.label,
      path: target.path,
      type: 'field',
      description: `Variable du catalogue (${field.sqlType}).`,
      // Le nom technique rejoint les mots-clés : cherché, jamais affiché.
      keywords: [field.name],
      // Le fil d'Ariane de la page visée, pour que la suggestion se situe comme les
      // autres. La clé peut être omise — les consommateurs traitent son absence comme
      // une liste vide — mais l'entrée remonte alors sans contexte.
      breadcrumb: target.breadcrumb,
    }));
  } catch (err) {
    console.warn(`build:search : champs non indexés — ${err.message}`);
    return [];
  }
}

function toIndexEntry(node) {
  return {
    title: node.name,
    path: node.path,
    type: node.type,
    description: node.description ?? '',
    keywords: node.keywords ?? [],
    breadcrumb: node.ancestors,
  };
}

async function main() {
  const siteConfig = JSON.parse(fs.readFileSync(CONFIG_PATH, 'utf8'));
  const { locales, defaultLocale } = siteConfig.site;

  const { resolveNavigationTree } = await importEsm(
    path.join(PROJECT_ROOT, 'src/utils/navigation/resolveNavigationTree.js'),
  );
  const { resolveLocalizedTree } = await importEsm(
    path.join(PROJECT_ROOT, 'src/utils/i18n/resolveLocalized.js'),
  );
  const { flattenNavigation } = await importEsm(
    path.join(PROJECT_ROOT, 'src/utils/navigation/flattenNavigation.js'),
  );
  const { DEMO_BASE_PATH } = await importEsm(
    path.join(PROJECT_ROOT, 'src/utils/navigation/basePaths.js'),
  );

  // UN INDEX PAR LANGUE : libellés ET chemins diffèrent d'une langue à l'autre.
  const indexes = [];
  for (const locale of locales) {
    const tree = resolveNavigationTree(
      resolveLocalizedTree(siteConfig.navigation.tree, locale, defaultLocale),
      `${DEMO_BASE_PATH}/${locale}`,
    );

    const entries = flattenNavigation(tree)
      .filter((node) => node.searchable)
      .map(toIndexEntry);

    // ─── AJOUT — les champs du catalogue, après les pages ────────────────────
    // Après, et non avant : à pertinence égale, une page doit sortir avant une variable.
    entries.push(...await buildFieldEntries(entries));

    indexes.push({ locale, entries });
  }

  fs.mkdirSync(OUTPUT_DIR, { recursive: true });

  for (const { locale, entries } of indexes) {
    fs.writeFileSync(
      path.join(OUTPUT_DIR, outputName(locale)),
      `${JSON.stringify(entries, null, 2)}\n`,
      'utf8',
    );
  }

  console.log(`build:search : ${indexes.length} index écrit(s)`);
}

main().catch((err) => {
  console.error('build:search : échec —', err.message);
  process.exit(1);
});
```

Rien à modifier côté composant : `keywords` est un champ apparié à part entière (poids 6,
entre le titre et le fil d'Ariane), et une entrée trouvée par mot-clé s'affiche sans
surlignage plutôt qu'avec un surlignage mensonger sur un titre où la requête n'apparaît
pas.

