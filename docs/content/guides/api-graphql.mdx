# Brancher l'API GraphQL

Brancher vos données tient en une variable d'environnement. Il n'y a **aucun bloc à
décommenter**, aucun composant à modifier, aucun hook à réécrire : le choix du transport se
fait en un seul point du projet, et tout ce qui est en aval l'ignore.

Cette page décrit le contrat **0.3.0** de l'API (`dashboard-template-api`). Si vous aviez
copié le template avant qu'il ne l'adopte, la dernière section, [Migrer depuis la version
précédente](#migrer-depuis-la-version-precedente), liste ce qui change et les fichiers à
reprendre.

## La seule variable : `NEXT_PUBLIC_API_URL`

`src/lib/api/client.js` sélectionne son transport à partir d'elle, et de rien d'autre :

```js
const transport = process.env.NEXT_PUBLIC_API_URL ? graphqlTransport : mockTransport;
```

Endpoint défini → l'API réelle. Endpoint absent → les fixtures locales de
`src/lib/api/fixtures/`. Copiez `.env.example` vers `.env.local` pour la renseigner :

```bash
NEXT_PUBLIC_API_URL=https://mon-api.exemple.org/graphql
```

Deux conséquences valent d'être énoncées, parce qu'elles sont exactement ce qui distingue ce
montage d'un « mode démo ».

**Le mode fixtures est un mode de fonctionnement, pas un repli sur erreur.** Une opération
sans fixture **lève**, et l'erreur remonte telle quelle jusqu'au composant. Rien ne masque
une panne d'API derrière des données de démonstration : les hooks renvoient un état vide
accompagné de leur `error`, et c'est au composant d'en faire quelque chose.

**Les hooks de `sources/` sont identiques dans les deux modes.** Ils appellent
`client.request(document, variables)` sans savoir qui répond. Ils sont donc lintés,
exécutés et éprouvés dans les deux modes — contrairement à un bloc commenté, qui pourrit
sans que personne s'en aperçoive.

**Le catalogue et le schéma sont des arguments de requête.** `catalog` et `schema` (les
coordonnées ducklake) voyagent dans `variables`, comme n'importe quel autre argument. Le
transport n'ajoute **aucun en-tête** : l'API ne lit plus `X-Catalog-Id` / `X-Schema-Id`, et
son CORS ne les autorise pas — les envoyer ferait échouer la requête de pré-vérification du
navigateur. L'API n'a pas d'authentification, donc pas d'en-tête `Authorization` non plus.

## Les trois modes de développement

| Commande | Source des données | Quand s'en servir |
|---|---|---|
| `npm run dev` | fixtures en mémoire, aucun appel réseau | Le défaut. Boucle de développement la plus rapide, aucun serveur à maintenir en vie. |
| `npm run dev:mock` | un vrai endpoint GraphQL local, `http://localhost:4000/graphql`, sur les mêmes fixtures | Voir l'application dialoguer avec un vrai serveur : cycle requête/réponse, onglet réseau, pagination — sans déployer l'API réelle. |
| `npm run dev:api` | votre API, via `NEXT_PUBLIC_API_URL` | Intégration finale sur données vivantes. |

`dev:mock` lance `scripts/mock-api-server.js` (graphql-yoga + `@graphql-tools/mock`) à côté
du serveur Next pointé sur lui. Ce serveur sert le **SDL réel de l'API**, figé dans
`scripts/schema.graphql`. Les six opérations que le template consomme y résolvent sur les
mêmes fixtures que `npm run dev` :

| Opération | Ce que le template en tire |
|---|---|
| `getFactTableWithMetadata` | les lignes, les métadonnées de leurs colonnes (`fields`) et la pagination |
| `getCatalogSchema` | les métadonnées de **tous** les champs, qui alimentent le menu de critères |
| `getSelectOptions` | les options plates d'un menu déroulant, recherchables côté serveur |
| `getSelectOptionsTree` | les options hiérarchiques (continent → pays) d'un menu groupé |
| `getFieldStats` | `min` / `max` / cardinalité d'une colonne, éventuellement sous un filtre |
| `getAggregates` | les valeurs agrégées d'un graphique, calculées sur tout le jeu filtré |

Elles honorent `limit`, `offset`, `sort` et `structuredFilters`, de sorte que la pagination,
le tri et le filtrage sont réellement exercés — le total d'un jeu filtré (`metadata.total`)
est celui des lignes retenues, comme sur l'API. Toute autre opération du schéma est
auto-mockée : valeurs arbitraires, mais conformes aux types, ce qui permet d'explorer le
reste du contrat sans l'implémenter. `npm run mock:api` lance le serveur seul.

Cette SDL figée sert une seconde fois : `npm run check:gql` **valide chaque document de
`src/lib/api/documents/` contre elle**, et fait échouer `npm run verify` si l'un d'eux
demande un champ qui n'existe pas. Vous ne pouvez pas livrer une requête qui ne compile pas
côté serveur.

## Épingler la version de l'API

Le template est développé et vérifié contre **une version précise** de l'API, jamais contre
« la dernière ». `scripts/schema.graphql` en est la copie, et elle ne s'édite pas à la main :

```bash
npm run sync:schema
```

La commande télécharge l'asset `schema.graphql` de la release épinglée de
`qbolliet/dashboard-template-api` (avec `gh` s'il est authentifié, par une requête HTTP
directe sinon), vérifie qu'il compile, puis réécrit le fichier en tête duquel elle consigne
la version et l'origine. Un SDL tronqué ou une page d'erreur ne remplace jamais la copie
saine. La version épinglée est `PINNED_REF` en tête de `scripts/sync-schema.js`, **committée** :
monter de version est un diff à relire, pas un « latest » implicite.

Trois variables d'environnement changent la source, pour la durée d'une commande :

| Variable | Effet |
|---|---|
| `API_SCHEMA_REF` | tag d'une autre release à télécharger (`v0.4.0`), au lieu de `PINNED_REF` |
| `API_SCHEMA_PATH` | chemin d'un `schema.graphql` local — typiquement un clone voisin de l'API, pour développer contre une version non publiée. L'en-tête du fichier signale alors « source locale » |
| `API_SCHEMA_REPO` | dépôt d'où télécharger, `qbolliet/dashboard-template-api` par défaut |

Pour passer à une nouvelle version de l'API :

```bash
API_SCHEMA_REF=v0.4.0 npm run sync:schema   # récupère le nouveau contrat
npm run check:gql                           # liste les documents qui ne compilent plus
```

Corrigez les documents signalés (et les résolveurs mock correspondants), puis changez
`PINNED_REF` pour que l'équipe entière se synchronise sur la même version. Si votre API
est un fork, pointez `API_SCHEMA_REPO` dessus, ou donnez `API_SCHEMA_PATH` ; l'important est
que le fichier reste une copie, régénérée, du schéma que votre serveur sert réellement.

## Ce que chaque feature attend

Les hooks de `sources/` ne reformatent rien : ils passent aux composants exactement ce que
l'API renvoie. Savoir ce qu'ils attendent, c'est donc savoir ce que votre API doit produire.

### Les métadonnées de colonne

Tout part de `Metadata`, l'objet qui décrit une colonne. Il arrive de deux façons — le champ
`fields` de `getFactTableWithMetadata` (les colonnes du jeu de résultats, alignées sur
`columns`) et `getCatalogSchema` (toutes les colonnes du catalogue) — avec la même forme,
en **camelCase** :

```json
[
  { "name": "gdp", "label": "Croissance du PIB (%)",
    "sqlType": "DOUBLE", "typeFamily": "NUMBER",
    "filterOperations": ["EQ", "NEQ", "GT", "GTE", "LT", "LTE", "BETWEEN", "NOT_BETWEEN",
                         "IN", "NOT_IN", "IS_NULL", "IS_NOT_NULL"],
    "isCategorical": false, "isPrimaryKey": false,
    "unit": "%", "displayFormat": ",.1f", "defaultAggregation": "AVG",
    "labelFor": null, "labelFields": [], "parentName": null },
  { "name": "country", "label": "Pays",
    "sqlType": "VARCHAR", "typeFamily": "TEXT",
    "filterOperations": ["EQ", "NEQ", "IEQ", "CONTAINS", "…", "IN", "NOT_IN", "IS_NULL", "IS_NOT_NULL"],
    "isCategorical": true, "isPrimaryKey": true,
    "unit": null, "displayFormat": null, "defaultAggregation": null,
    "labelFor": null, "labelFields": [], "parentName": "region" }
]
```

Le template **ne lit jamais `sqlType`** : c'est le type physique de la base (`DOUBLE`,
`UBIGINT`, `DECIMAL(18,2)`…), affiché tel quel au mieux. Les décisions se prennent sur la
**famille de type**, que le serveur calcule :

| `typeFamily` | Types SQL | Widget de valeur du filtre | Traitement par le graphique |
|---|---|---|---|
| `INTEGER` | `TINYINT` … `UHUGEINT` | champ numérique, pas entier | nombre |
| `NUMBER` | `FLOAT`, `DOUBLE`, `DECIMAL` | champ numérique | nombre |
| `DATE` | `DATE` | sélecteur de date | date |
| `TIMESTAMP` | `TIMESTAMP` et variantes | sélecteur de date | date |
| `TEXT` | `VARCHAR` | saisie texte ou menu si `isCategorical` | catégorie |
| `BOOLEAN` | `BOOLEAN` | saisie texte (`EQ` seul) | catégorie |
| `OTHER` | `TIME`, `INTERVAL`, `UUID`… | aucun (seuls `IS_NULL` / `IS_NOT_NULL` existent) | catégorie |

Un entier ou un nombre marqué `isCategorical` est traité en catégorie par le graphique, comme
un texte. Les autres champs, dans l'ordre où ils servent :

- `filterOperations` — les opérations que **l'API accepte sur cette colonne**, en
  majuscules (`EQ`, `GT`, `BETWEEN`, `IN`, `CONTAINS`…). C'est la source de vérité de ce que
  le menu de critères propose ; plus aucune liste d'opérations par type n'est écrite côté
  client.
- `isCategorical` — la colonne a peu de valeurs distinctes : le menu de critères propose un
  menu de valeurs (`IN`) plutôt qu'une saisie libre, et le graphique la traite en catégorie.
- `unit` et `displayFormat` — l'unité (`%`, `€`) et un format d3 (`,.1f`, `.1%`) qui
  mettent en forme les axes, les infobulles et les cellules numériques.
- `defaultAggregation` — l'agrégation naturelle d'une mesure (`SUM` d'un stock, `AVG` d'un
  taux). Elle dit à `getAggregates` comment regrouper quand on ne précise rien.
- `labelFor` / `labelFields` — une colonne de libellés (`labelFor: "indicator"`) décrit le
  code d'une autre ; le code, lui, liste ses colonnes de libellés. Un libellé n'est pas une
  variable à filtrer : le menu de critères l'écarte, le tableau peut le replier dans la colonne
  du code (`codeLabels`).
- `parentName` — la colonne parente dans une hiérarchie (`country` → `region`). Un champ qui
  a un parent est servi en menu groupé.

### Chart — `useFactTable`, `useAggregatedChart`

`getFactTableWithMetadata(format: OBJECTS)` renvoie `columns`, `fields`, `data` et
`metadata`. `data` est un tableau d'**objets** dont les clés sont les noms de colonnes — le
format long, passé **tel quel** à `<Chart data={rows} />`. Passez aussi `fields` à
`<Chart fields={fields} />` : le type de chaque colonne vient alors de sa `typeFamily`, au
lieu d'être deviné sur un échantillon de valeurs (un code `'01012100'` reste une chaîne), et
l'axe et l'infobulle d'une mesure suivent son `displayFormat` et son `unit`. Sans `fields`,
le comportement antérieur — détection sur les valeurs — s'applique ; une prop `format`
explicite l'emporte toujours.

```json
{
  "columns": ["date_obs", "country", "gdp"],
  "fields": [ { "name": "date_obs", "typeFamily": "DATE" }, "…" ],
  "data": [
    { "date_obs": "2024-01-01", "country": "France", "gdp": 101.4 },
    { "date_obs": "2024-04-01", "country": "France", "gdp": 102.8 }
  ],
  "metadata": {
    "count": 2, "total": 240,
    "extents": { "gdp": [98.0, 112.2], "date_obs": ["2024-01-01", "2024-04-01"] },
    "hasNextPage": true, "currentPage": 1, "totalPages": 120,
    "generatedAt": "2026-08-07T09:12:00Z"
  }
}
```

Deux nombres se ressemblent et ne disent pas la même chose : `metadata.count` est le nombre de
lignes **de la page**, `metadata.total` celui des lignes **retenues par le filtre**. Pour un
texte « sur N au total », c'est `total`. De même, `metadata.extents` donne les bornes
`[min, max]` des colonnes numériques et des dates **de la page seulement**. Les bornes du jeu
entier — ou du jeu filtré — viennent de `getFieldStats` (voir plus bas).

**Un graphique qui regroupe ne se trace pas depuis une page de lignes.** Des barres, un
empilement, une heatmap ou une série temporelle agrégée doivent porter sur tout le jeu
filtré : une page de 100 lignes en donnerait une image fausse. C'est `getAggregates` qui
fait ce calcul, côté serveur, et le hook `useAggregatedChart` fait le pont :

```jsx
const chart = useAggregatedChart({
  x: 'date_obs', measures: ['gdp'], hue: 'country',
  fields, structuredFilters,
});

<Chart {...chart.chartProps} />
```

Le hook décide qui agrège : pour les tracés qui regroupent, il interroge `getAggregates`
(une ligne par groupe, la valeur dans `y`) et pose la prop `aggregate` sur `<Chart>`, qui
rend alors chaque valeur telle quelle sans jamais la ré-agréger ; pour les autres (nuage,
violon, densité), il charge lui-même les lignes brutes des seules colonnes tracées (ou prend
celles passées en `rows`). Chaque mesure est agrégée par sa
`defaultAggregation` ; plusieurs mesures sont tracées en format long (une série par mesure).
`chart.truncated` signale qu'il y avait plus de groupes que le plafond de 1000 d'une requête.
`<Chart>` lui-même ne fait aucune requête : il reste installable seul depuis le registry.

Sur des **lignes brutes**, un tracé qui regroupe (barres, heatmap) réduit lui-même ses
lignes avec la `defaultAggregation` de la mesure, et la moyenne quand elle n'en déclare pas
— c'était l'unique comportement avant.

### Table — `useFactTableWithMetadata`

Le tableau a besoin des **lignes** et du **schéma de colonnes**, et un seul appel suffit :
`fields` de `getFactTableWithMetadata`. Le hook les expose sous `data` et `columnsMetadata`,
passés tels quels aux props du même nom de `<Table>` — c'est ce qui lui permet de dériver
ses colonnes, ses libellés, l'alignement des nombres, leur `displayFormat` et leur `unit`, et
ses filtres tout seul. `codeLabels` replie une colonne de libellés dans celle de son code
(« 01012100 — Chevaux reproducteurs ») ; le tri, les filtres et les exports gardent le code.

**Mode distant.** Quand les lignes viennent de l'API, le filtrage doit se faire sur
l'API : filtrer les 100 lignes chargées ne dirait rien des 10 000 autres. Passez
`columnFilters` et `onColumnFiltersChange` pour que le tableau cesse de rien évaluer et
affiche ce qu'il reçoit. Vous gardez les sélections de colonne, les convertissez avec
`columnCriteria`, les combinez au filtre du menu avec `andNodes`, et envoyez le tout en
`structuredFilters` (voir la section suivante). L'entonnoir d'une colonne liste alors ses
valeurs par `getSelectOptions`. Le montage complet est dans l'exemple `table-api`, et
`IndicatorExplorer` en est la version de production.

### Filtrer côté serveur : `structuredFilters`

Aucun filtre n'est évalué sur les lignes chargées. Le menu de critères produit un arbre, que
`toFilterNode` convertit en **`FilterNode`**, l'argument `structuredFilters` de
`getFactTableWithMetadata`, `getAggregates` et `getFieldStats`. Un nœud est soit une feuille
(`criterion`), soit un groupe (`children`) ; le connecteur est porté par le nœud, il lie
celui-ci au précédent du même groupe, et se lit avec la précédence SQL (`ET` avant `OU`).
Les sous-groupes sont parenthésés, `negate` inverse un nœud.

```json
{
  "children": [
    { "criterion": { "variable": "country", "operation": "IN", "value": ["France", "Italie"] } },
    { "connector": "AND",
      "criterion": { "variable": "gdp", "operation": "BETWEEN", "value": { "min": -2, "max": 5 } } },
    { "connector": "OR",
      "criterion": { "variable": "date_obs", "operation": "AFTER", "value": "2024-01-01" } }
  ]
}
```

La forme de `value` dépend de l'opération : un scalaire pour une comparaison, un tableau non
vide pour `IN` / `NOT_IN`, un objet `{ min, max }` pour `BETWEEN`, rien pour `IS_NULL`. Les
dates sont des chaînes ISO 8601 — `toFilterNode` convertit la saisie selon l'ordre de la
langue (`dateOrder`) — et les entiers au-delà de 2^53 voyagent en chaînes pour ne pas perdre
de précision. L'API **rejette** un critère incomplet : `toFilterNode` les omet, avec les
groupes qu'ils laissent vides, et une expression dont les parenthèses ne se ferment pas ne
donne aucun filtre.

Les filtres de colonne du tableau (`columnCriteria`, un critère `IN` par colonne) se combinent
au filtre du menu par `andNodes`, qui garde le filtre du menu en sous-groupe pour que le `OU`
d'un côté ne contamine pas le `ET` de l'autre. Graphique, tableau et indicateurs reçoivent
alors **le même** `structuredFilters` et montrent donc le même sous-jeu.

### Filter — `useVariableMetadata`

`getCatalogSchema(catalog, schema)` décrit chaque champ, et ces métadonnées pilotent
directement le menu de critères : la famille de type détermine le widget de saisie, et
`filterOperations` les opérations offertes.

`metadataToVariables()` transpose les métadonnées en la forme attendue par `CriterionMenu` et
`MultiCriterionMenu` — `{ value, label, typeFamily, isCategorical, filterOperations }` — en
écartant les colonnes de libellés. Les **libellés** des opérations ne viennent pas de l'API
mais de `config/filter/operations.json`, indexé par valeur de l'enum : le fichier ne dit pas
*quelles* opérations proposer (c'est `filterOperations`), il dit comment les nommer.
`resolveOperationLabels` l'aplatit dans la langue courante et le résultat se passe à la prop
`operationLabels`. Une opération sans libellé s'affiche sous sa valeur d'enum (`NOT_BETWEEN`).
Le composant propose l'intersection de ce que l'API accepte et de ce que son widget sait
saisir ; ainsi une colonne `OTHER` ne propose aucune opération.

### Les options des menus déroulants

Les menus de valeurs sont servis par `getSelectOptions` (options plates, recherchables côté
serveur par `searchTerm`) et par `getSelectOptionsTree` (arbre `[{ value, label, children? }]`
d'une hiérarchie de colonnes, par exemple continent → pays). Le mode groupé est **déduit des
métadonnées** : un champ qui déclare un `parentName` est servi en arbre, que le serveur remonte
lui-même d'après la chaîne des parents ; `groupField` ne fait que forcer ce mode, et sa valeur
n'est pas envoyée à l'API ; un appelant qui connaît déjà le `parentName` passe `grouped` et
évite la requête de schéma. L'arbre n'a pas de `limit` — l'API rejette un arbre trop grand
plutôt que de le tronquer — : chargé une fois, il est complet, et la recherche s'y fait
localement. Une liste plate est demandée avec une option de plus que les 50 affichées : si
elle n'arrive pas, la liste est complète et la recherche reste locale ; sinon le terme part
à l'API. Dans les deux cas la règle est celle du serveur : le code ou le libellé.

Les deux requêtes acceptent `structuredFilters`, le même `FilterNode` que `getFieldStats` :
il restreint les lignes lues **avant** le `SELECT DISTINCT`, si bien que seules les valeurs
portées par une ligne qui le satisfait reviennent (l'arbre est élagué des branches vides) ;
`searchTerm` et `limit` s'appliquent ensuite, inchangés. `useSelectOptions` l'envoie quand il
reçoit un périmètre (`scopeFilters`, prop de `SelectMenu`) et l'ajoute à sa clé de cache sous
forme de JSON ; sans périmètre, la requête et la clé sont exactement celles d'un menu global,
qui partagent donc le même cache. Comme pour les bornes, ce n'est jamais le filtre courant —
il contient le critère que le menu édite — mais :

- le périmètre explicite d'un `SelectMenu` isolé (`scopeFilters`, par exemple le pays de la
  page) ;
- dans un `MultiCriterionMenu`, le filtre des **autres** critères (`scopeWithout`), sauf
  `dependentValues={false}`. Un périmètre vide donne un menu vide, sans repli sur les options
  globales ; une valeur déjà choisie qu'il exclut reste choisie — voir « Valeurs proposées »
  dans la page du filtre.

### Les bornes d'une colonne : `getFieldStats`

`getFieldStats(fieldName, structuredFilters)` renvoie `min`, `max`, `distinctCount` et
`nullCount` d'**une** colonne, sur tout le jeu ou sur le jeu filtré. C'est de là que viennent
les bornes d'un slider (`ConstraintField` avec `fieldName`, via `useRangeBounds` ; son pas se
déduit de la famille de type et du `displayFormat`) et les indicateurs de cadrage d'une page :

- « observations » est `metadata.total` ;
- la « période » et l'« amplitude » sont les `MIN` / `MAX` de l'abscisse et de la mesure,
  **sous le filtre courant**, lus dans un seul `getAggregates` sans `groupBy` (quatre agrégats,
  une ligne) plutôt que dans deux `getFieldStats`, et seulement pour les colonnes numériques ou
  dates — le `min` d'une colonne texte est un minimum lexical, qui ne veut rien dire ici.

Les bornes d'un slider de critère, elles, ne portent jamais sur le filtre courant : il contient
le critère lui-même, et ses bornes se refermeraient sur la sélection. Elles portent sur toute la
colonne, sauf deux cas, chacun envoyé en `structuredFilters` à `getFieldStats` :

- un `ConstraintField` isolé peut être borné à un périmètre par `scopeFilters` (piste et
  validation) ;
- dans un `MultiCriterionMenu`, la **piste** de chaque carte suit le filtre des **autres**
  critères (`scopeWithout`, prop `trackScope` de `ConstraintField`), la validation restant sur toute la
  colonne — voir « Valeurs proposées » dans la page du filtre.

`Metadata.stats` n'est volontairement pas sélectionné dans les documents de faits et de
schéma : l'API le calcule à la demande, une requête SQL par colonne.

### L'export du jeu complet

Une page de lignes n'est pas le jeu. Quand le tableau est adossé à l'API — mode distant, et
`NEXT_PUBLIC_API_URL` ou `queryHint.apiBase` défini —, ses boutons CSV et Parquet
téléchargent le **jeu filtré entier** par `/api/export` de l'API, avec les colonnes visibles
dans l'ordre, le tri et le filtre courants. La requête est un `GET` dont l'URL se copie et se
partage ; au-delà de 4000 caractères (une longue liste `IN`), elle passe en `POST` avec les mêmes
paramètres dans un corps JSON. Les refus de l'API sont annoncés dans la langue de
l'interface : jeu trop volumineux (filtrez-le), trop d'exports simultanés (réessayez dans N
secondes), API injoignable. La barre d'outils offre aussi de copier la commande cURL de
l'export complet, à côté des extraits `fetch`, Python et cURL de la requête GraphQL.

Sur des **données statiques**, sans API, l'export CSV porte sur les lignes chargées, côté
client, et le bouton Parquet est masqué tant que vous ne fournissez pas `onExportParquet`
(une route ou une action serveur).

### Le rendu serveur : `requestSafe`

Les pages générées sont prérendues au build. Une requête qui lève pendant le prérendu fait
**échouer le build entier** — inacceptable pour un template que des tiers embarquent, où une
API momentanément injoignable ne doit jamais avoir cet effet.

`src/lib/api/serverRequest.js` expose donc `requestSafe`, qui renvoie `null` au lieu de
propager, en journalisant l'échec dans la sortie de `next build`. Le composant rend alors
son état dégradé, et l'îlot client refait la requête au montage. **Côté serveur uniquement** :
côté client, les hooks SWR gèrent déjà cache, déduplication et revalidation.

## Ajouter un document GraphQL

Quatre gestes, dont un facultatif.

**1 — Le document**, dans `src/lib/api/documents/`. Le tag `gql` est une identité locale :
il ne fait qu'assembler la chaîne, mais il permet aux éditeurs de colorer le bloc et au
vérificateur de l'extraire.

**2 — L'export**, dans `documents/index.js`. C'est le point d'entrée unique des hooks.

**3 — Le résolveur mock**, en deux endroits. La logique vit dans `transports/mockResolvers.js`,
dans l'objet que renvoie `createMockResolvers`, indexée par **champ racine** du schéma
(`getLastRefresh`). `transports/mock.js` associe ensuite le **nom d'opération** du document
— l'identifiant qui suit `query` — à ce champ racine, dans son objet `OPERATIONS`. Sans cette
ligne, le mode par défaut lève sur votre nouvelle opération. Le serveur `npm run dev:mock`
réutilise les mêmes résolveurs : il n'y a rien à ajouter pour lui.

**4 — Un test du résolveur** (facultatif mais recommandé), à côté, sur le modèle de
`mockResolvers.aggregates.test.js`.

Puis `npm run check:gql` valide le document contre `scripts/schema.graphql`. Si votre API
diverge de cette SDL, régénérez le fichier (voir [Épingler la version de
l'API](#epingler-la-version-de-l-api)) plutôt que de l'éditer.

## Exemple complet

Ajouter une opération `getLastRefresh`, qui renvoie la date de dernière actualisation d'un
catalogue, et l'afficher dans une page.

```js
// 1 — src/lib/api/documents/lastRefresh.js
import { gql } from './gql';

// =================================================================
// DOCUMENT — getLastRefresh
// =================================================================
// Date de dernière actualisation du catalogue. Opération de métadonnées : pas de
// pagination, pas de filtres, un seul objet en retour.

/**
 * `getLastRefresh` query document.
 *
 * @type {string}
 */
export const GET_LAST_REFRESH = gql`
  query GetLastRefresh($catalog: String, $schema: String) {
    getLastRefresh(catalog: $catalog, schema: $schema) {
      refreshedAt
      rowCount
    }
  }
`;
```

```js
// 2 — src/lib/api/documents/index.js — ajouter la ligne
export { GET_LAST_REFRESH } from './lastRefresh';
```

```js
// 3a — src/lib/api/transports/mockResolvers.js — dans l'objet renvoyé par
// createMockResolvers. La clé est le CHAMP RACINE du schéma. Le résolveur reçoit les
// arguments de la requête ; `catalogueId` désigne le catalogue documentaire, tout autre
// catalogue retombe sur le panel macro, comme le fait `datasetOf`.
getLastRefresh: ({ catalog }) => {
  const isCatalogue = catalog === catalogueId;
  return {
    refreshedAt: isCatalogue ? '2026-08-01T04:00:00Z' : '2026-08-06T04:00:00Z',

  };
},

// 3b — src/lib/api/transports/mock.js — nom d'OPÉRATION (`query GetLastRefresh`) → champ racine.
// La réponse arrive dans une microtâche, ce qui fait passer les composants par le même

const OPERATIONS = {
  // …
  GetLastRefresh: 'getLastRefresh',
};
```

```js
// 4 — src/features/table/sources/useLastRefresh.js
import useSWR from 'swr';
import { request } from '@/lib/api/client';
import { GET_LAST_REFRESH } from '@/lib/api/documents';

// =================================================================
// SOURCE — DERNIÈRE ACTUALISATION
// =================================================================
// Le transport est choisi une fois pour toutes dans lib/api/client.js : ce hook est
// identique en mode fixtures et en mode API. `catalog` / `schema` sont les coordonnées
// ducklake, de simples arguments de requête : ils voyagent dans `variables`, jamais en
// en-têtes.

function fetchLastRefresh([, catalog, schema]) {
  return request(GET_LAST_REFRESH, { catalog, schema })
    .then((data) => data.getLastRefresh);
}

/**
 * Fetches the last refresh date of a catalog.
 *
 * Backed by SWR: caches and deduplicates requests sharing the same
 * `['lastRefresh', catalog, schema]` key across component instances.
 *
 * @param {Object} [params]
 * @param {string} [params.catalog] - Ducklake catalog.
 * @param {string} [params.schema] - Ducklake schema.
 * @returns {{refreshedAt: (string|null), rowCount: (number|null), loading: boolean, error: (Error|null)}}
 */
export function useLastRefresh({ catalog, schema } = {}) {
  const { data, error, isLoading } = useSWR(['lastRefresh', catalog, schema], fetchLastRefresh);

  // En cas d'échec, on renvoie un état vide + `error` : masquer la panne derrière une
  // date de démonstration tromperait le consommateur.
  if (error) {
    return { refreshedAt: null, rowCount: null, loading: isLoading, error };
  }

  return {
    refreshedAt: data?.refreshedAt ?? null,
    rowCount: data?.rowCount ?? null,
    loading: isLoading,
    error: null,
  };
}
```

```jsx
// 5 — consommation dans un composant client
'use client';

import { useLastRefresh } from '@/features/table/sources/useLastRefresh';

const RefreshNotice = ({ catalog }) => {
  const { refreshedAt, rowCount, loading, error } = useLastRefresh({ catalog });

  if (loading) return <p>Chargement…</p>;
  if (error) return <p role="alert">Actualisation inconnue : {error.message}</p>;

  return (
    <p>
      {rowCount} lignes, actualisées le{' '}
      <time dateTime={refreshedAt}>{new Date(refreshedAt).toLocaleDateString('fr')}</time>
    </p>
  );
};

export default RefreshNotice;
```

## Migrer depuis la version précédente

Cette section s'adresse à qui a **copié le template avant le contrat 0.3.0** (ou installé
des items du registry) et souhaite le rattraper. Le détail, version par version, est dans
le `CHANGELOG.md` ; voici ce qui compte pour s'y retrouver.

**Ce qui a changé dans les données.**

| Avant | Maintenant |
|---|---|
| métadonnées en `snake_case` : `sql_type`, `is_categorical`, `is_primary_key`, `python_type` | `camelCase` : `sqlType`, `isCategorical`, `isPrimaryKey` ; `python_type` disparaît |
| décisions sur le **type SQL** (`double precision`, `integer`, `character varying`…) | décisions sur la **famille de type** : `typeFamily` (`INTEGER`, `NUMBER`, `DATE`, `TIMESTAMP`, `TEXT`, `BOOLEAN`, `OTHER`) |
| opérations en minuscules (`gte`, `between`, `in`) | valeurs de l'enum `FilterOperation`, en majuscules (`GTE`, `BETWEEN`, `IN`) |
| `operations.json` : listes d'opérations **par type SQL**, prop `operationsByType` | `operations.json` : **libellés** seuls, indexés par opération ; prop `operationLabels` ; les opérations offertes viennent de `filterOperations` |
| en-têtes `X-Catalog-Id` / `X-Schema-Id` | `catalog` / `schema` en arguments de requête, aucun en-tête |
| `request(document, variables, { catalog, schema })` | `request(document, variables)` |
| `getGroupedSelectOptions` | `getSelectOptionsTree` ; mode groupé déduit de `parentName` |
| deux requêtes parallèles (lignes + schéma) | un seul appel : `fields` accompagne les lignes |
| filtre évalué sur les lignes chargées (`evalFilterNode`) | filtre envoyé à l'API en `structuredFilters` |
| export des lignes chargées | export du jeu filtré entier par `/api/export` |
| formatage par type deviné, `format` à la main | `displayFormat` / `unit` des métadonnées, via `fields` |
| moyenne des lignes pour un graphique qui regroupe | `defaultAggregation` de la mesure, calculée par `getAggregates` |

**Les fichiers à reprendre**, par ordre d'importance :

1. `scripts/schema.graphql` (par `npm run sync:schema`) et `scripts/sync-schema.js`, puis
   `npm run check:gql` : il énumère précisément les documents qui ne compilent plus.
2. `src/lib/api/documents/` — tous les documents. Si vous en avez ajouté, adaptez-les à
   `camelCase` et aux nouveaux arguments.
3. `src/lib/api/transports/` — le transport GraphQL ne pose plus d'en-têtes ; le mock
   (`mock.js`, `mockResolvers.js`) et `fixtures/` suivent le nouveau contrat. Si vous avez
   branché des fixtures à vous, donnez-leur `typeFamily` et `filterOperations`
   (`fixtures/metadata.js` rejoue la dérivation du serveur).
4. `src/features/filter/utils/filterTypes.js`, `filterEngine.js` et
   `config/filter/operations.json` — le catalogue d'opérations par type SQL disparaît.
5. Les hooks `sources/` de `chart`, `table` et `filter`, puis `Table`, `Chart`, `CriterionMenu`
   et `MultiCriterionMenu` qui lisent les nouveaux noms.

**Dans votre propre code**, remplacez `operationsByType={…}` par `operationLabels={…}`
(`resolveOperationLabels(operations, locale, defaultLocale)`), `sql_type` / `is_categorical`
par `typeFamily` / `isCategorical` dans les variables, les opérations minuscules par leurs
équivalents majuscules dans les critères initiaux, et supprimez tout filtrage côté client de
données qui viennent de l'API — il faut désormais passer `structuredFilters` au hook. Un
critère initial en minuscules n'est plus reconnu : son libellé retombe sur la valeur brute
et l'opération n'est pas sélectionnée.
