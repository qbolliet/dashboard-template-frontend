# Installation

Deux voies, selon ce que vous avez déjà.

**Vous démarrez un tableau de bord** : partez du dépôt modèle. Vous récupérez l'ensemble —
la navigation, les features, le système de tokens, l'outillage de vérification, la démo et
cette documentation — dans un dépôt neuf qui vous appartient.

**Vous avez déjà une application Next.js** : piochez dans le registry. La CLI copie les
fichiers d'un composant dans votre arborescence, installe ses dépendances npm et tire ses
dépendances internes. Vous n'embarquez que ce que vous demandez.

Le **fork**, lui, ne convient à aucun des deux : il crée un lien permanent vers ce dépôt —
historique commun, réseau GitHub partagé, issues et PR routées vers le parent — alors que
vous ne rapatrierez jamais nos refontes internes dans le tableau de bord de votre client.
C'est l'outil de la contribution en retour, pas celui du démarrage de projet.

## Nouveau projet — le dépôt modèle

Le bouton **« Use this template »** de la page GitHub du dépôt crée une copie complète avec
un **historique vierge** et aucun lien vers le parent. En ligne de commande :

```bash
gh repo create mon-dashboard --template qbolliet/dashboard-template-frontend --private --clone
cd mon-dashboard
npm install
npm run dev
```

Node 22 ou plus est requis : les scripts de build chargent des modules ESM par détection de
syntaxe, ce que les versions antérieures ne font pas.

`npm run dev` lance les cinq générateurs (index de recherche, registry, tables de props,
index de la documentation, référence des tokens) puis le serveur de développement :

| URL | Ce que vous y trouvez |
|---|---|
| `http://localhost:3000/` | cette documentation, servie par votre propre copie |
| `http://localhost:3000/demo` | l'application de démonstration, générée depuis `config/site.config.json` |

Aucune configuration n'est nécessaire pour cette première exécution : sans
`NEXT_PUBLIC_API_URL`, l'application sert les fixtures locales de `src/lib/api/fixtures/`.
C'est un mode de fonctionnement à part entière, pas un repli sur erreur — voir
[Brancher l'API GraphQL](/guides/api-graphql).

### Détacher votre projet de cette documentation

Ce partage — la documentation à la racine, votre application sous `/demo` — est celui du
dépôt modèle, pas celui de votre projet. `npm run eject` le renverse en une commande :
votre application remonte à la racine et la documentation est retirée (ou conservée sous
`/docs` avec `--keep-docs`). L'opération exige un arbre git propre, dont le diff est le seul
retour arrière. Le choix des modes, la procédure et la checklist de publication sont dans
[Partir du template](/guides/partir-du-template).

## Projet existant — la CLI du registry

Chaque composant, feature et bloc de ce dépôt est publié comme item de registry au format
`shadcn`, servi par les mêmes GitHub Pages que cette documentation. Il n'y a pas de CLI
propre à installer : `npx shadcn` sait consommer un registry tiers par URL.

```bash
npx shadcn@latest add https://qbolliet.github.io/dashboard-template-frontend/r/stat-card.json
```

Les items sont publiés en `registry:item` et **chaque fichier porte un `target` explicite**.
C'est ce couple qui les rend universels au sens de shadcn : la CLI les installe sans exiger
de `components.json`, sans détection de framework et **sans Tailwind**. Les fichiers
atterrissent sous `~/`, c'est-à-dire à la racine de votre projet, en reproduisant
l'arborescence du dépôt — `src/components/ui/StatCard/…` ici devient
`src/components/ui/StatCard/…` chez vous.

Chaque item déclare aussi :

- ses **dépendances npm** réelles, dérivées par analyse statique des imports de son
  sous-arbre — la CLI les installe ;
- ses **dépendances internes** (`registryDependencies`), en URL absolues, que la CLI
  résout et installe transitivement. Demander `chart` installe donc aussi `api-client`,
  `icons`, `hover-toolbar`, `tokens-global` et les autres, sans que vous ayez à les
  connaître.

L'index complet des items se trouve à
[`/r/registry.json`](https://qbolliet.github.io/dashboard-template-frontend/r/registry.json),
et le nom d'item de chaque composant figure en tête de sa page dans
[Composants](/composants) et [Features](/features).

### Les deux réglages à faire une fois

Les fichiers installés sont copiés **verbatim**, avec les chemins d'import du dépôt. Deux
conventions doivent donc exister dans votre projet, une seule fois, avant le premier item.

**1 — L'alias `@/`.** Tout import inter-dossiers du template passe par `@/`, y compris dans
les feuilles SCSS (`@use '@/styles/globals/tokens/semantic-colors' as *;`). Déclarez-le dans
votre `jsconfig.json` ou `tsconfig.json` :

```jsonc
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

**2 — Les tokens globaux.** L'item `tokens-global` apporte les primitives, les tokens
sémantiques, l'échelle typographique et les mixins de points de rupture. Il est tiré
automatiquement par presque tous les autres items, mais **personne ne peut importer votre
feuille globale à votre place** : ajoutez la ligne vous-même.

```scss
/* src/app/globals.scss */
@use '@/styles/globals/custom-properties';
```

Sans elle, les composants s'affichent sans aucune couleur ni dimension : leurs tokens de
niveau 3 et 4 pointent vers des rôles qui n'existent pas.

### Ce que vous récupérez, et ce que vous en faites

Le code installé **vous appartient**. Il est dans votre dépôt, vous l'éditez, et vous n'avez
aucune mise à jour à absorber. C'est le corollaire assumé de ce mode de distribution : il
n'y a pas de `node_modules` à mettre à jour, donc pas non plus de mise à jour qui casse —
mais rien ne vous signalera non plus qu'un correctif est sorti. Relancer la commande `add`
réinstalle l'item dans sa version courante, en écrasant vos modifications : faites-le sur
un arbre de travail propre, et relisez le diff.

Avant d'éditer un fichier pour changer une apparence, lisez tout de même
[Theming](/fondations/theming) : les trois premiers niveaux d'intervention obtiennent le
résultat sans toucher au code installé, ce qui garde votre copie comparable à la nôtre.

## Exemple complet

Ajouter un graphique filtrable et son tableau à une application Next.js existante, de zéro
au premier rendu.

```bash
# 1 — Les items. `filter` et `table` tirent `api-client` et `tokens-global` d'eux-mêmes.
npx shadcn@latest add https://qbolliet.github.io/dashboard-template-frontend/r/chart.json
npx shadcn@latest add https://qbolliet.github.io/dashboard-template-frontend/r/filter.json
npx shadcn@latest add https://qbolliet.github.io/dashboard-template-frontend/r/table.json

# 2 — L'endpoint GraphQL. Omettez cette ligne pour travailler sur les fixtures livrées.
echo 'NEXT_PUBLIC_API_URL=https://mon-api.exemple.org/graphql' >> .env.local
```

```jsonc
// 3 — jsconfig.json (ou tsconfig.json) : l'alias qu'utilisent les fichiers installés.
{
  "compilerOptions": {
    "paths": { "@/*": ["./src/*"] }
  }
}
```

```scss
/* 4 — src/app/globals.scss : les tokens, avant tout le reste. */
@use '@/styles/globals/custom-properties';
```

```jsx
// 5 — src/app/indicateurs/page.jsx
'use client';

import { useState } from 'react';
import { Chart, useAggregatedChart } from '@/features/chart';
import { Table, useFactTableWithMetadata } from '@/features/table';
import { MultiCriterionMenu } from '@/features/filter';
import { toFilterNode, columnCriteria, andNodes } from '@/features/filter/utils/filterEngine';
import { metadataToVariables } from '@/features/filter/sources/useVariableMetadata';

// Libellés des opérations, indexés par valeur de l'enum FilterOperation de l'API. Ils ne
// disent PAS quelles opérations proposer : cette liste vient de `filterOperations`, dans les
// métadonnées de chaque colonne. Le dépôt modèle livre un catalogue complet, bilingue, en
// `config/filter/operations.json` — l'item de registry, non, car c'est un choix éditorial.
// Une opération sans libellé s'affiche sous sa valeur d'enum.
const OPERATION_LABELS = {
  EQ: '=', GT: '>', GTE: '≥', LT: '<', LTE: '≤',
  BETWEEN: 'Entre', IN: 'IN', NOT_IN: 'NOT IN',
};

const IndicateursPage = () => {
  // Valeur structurée du menu de critères — un ARBRE de critères, pas une liste plate.
  const [filter, setFilter] = useState(null);
  // Sélections des filtres de colonne du tableau (mode distant de <Table>)
  const [columnFilters, setColumnFilters] = useState({});

  // Schéma des colonnes (`fields` de l'API : nom, libellé, famille de type, opérations
  // acceptées, format…). Requête non filtrée, dont la clé SWR est aussi celle de la requête
  // filtrée tant qu'aucun filtre n'est posé.
  const { columnsMetadata: fields } = useFactTableWithMetadata();

  // Le filtre est envoyé à l'API, jamais appliqué aux lignes chargées : le menu et les
  // filtres de colonne forment ensemble un seul FilterNode (`structuredFilters`).
  const menuNode = filter ? toFilterNode(filter.tree, { balanced: filter.balanced }) : null;
  const columns = fields.map(({ name, typeFamily }) => ({ key: name, typeFamily }));
  const structuredFilters = andNodes(menuNode, columnCriteria(columnFilters, columns));

  // Page de lignes du jeu filtré, pour le tableau.
  const { data } = useFactTableWithMetadata({ structuredFilters });

  // Variables filtrables : toutes les colonnes sauf les colonnes de libellés.
  const variables = metadataToVariables(fields);

  // Props de <Chart>. Un graphique qui regroupe est tracé depuis `getAggregates`, sur tout le
  // jeu filtré (agrégation déclarée de la mesure) et non depuis la page de lignes du tableau ;
  // les autres (nuage, violon…) reçoivent les lignes brutes.
  const chart = useAggregatedChart({
    x: 'date_obs', measures: ['gdp'], hue: 'country', fields, rows: data, structuredFilters,
  });

  return (
    <main>
      <MultiCriterionMenu
        variables={variables}
        operationLabels={OPERATION_LABELS}
        structuredFilters={structuredFilters}
        onChange={setFilter} />

      <Chart {...chart.chartProps} height={420} />

      <Table
        data={data}
        columnsMetadata={fields}
        columnFilters={columnFilters}
        onColumnFiltersChange={setColumnFilters}
        queryHint={{ operation: 'getFactTableWithMetadata', structuredFilters: menuNode }}
        title="Indicateurs macroéconomiques" />
    </main>
  );
};

export default IndicateursPage;
```

Trois points que cet exemple illustre et qui valent au-delà de lui. Le filtre est un
**arbre**, pas une liste plate, et il est évalué **par l'API** : `toFilterNode` le convertit en
`structuredFilters`, que reçoivent le tableau, le graphique et le champ de bornes du menu —
tous montrent donc le même sous-jeu, y compris au-delà de la première page. Les types ne sont
pas devinés : `fields` porte la famille de type de chaque colonne, que le menu, le tableau et le
graphique lisent. Et l'agrégation d'un graphique qui regroupe est faite par l'API aussi. Le
gabarit `IndicatorPage` du dépôt modèle est exactement ce montage, en plus complet — sélecteur
de mesures, indicateurs de cadrage, export, textes localisés. Le détail du contrat est dans
[Brancher l'API GraphQL](/guides/api-graphql).

Les props de chaque composant sont dans sa page, lues dans le code au build plutôt que
rédigées : [Chart](/features/chart), [Table](/features/table), [Filter](/features/filter).
